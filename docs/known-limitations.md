# Nian Vision v1 known limitations

These are intentional v1 boundaries, not hidden roadmap promises.

- **Platforms:** Windows x86_64 and Linux x86_64 only. No macOS or mobile release.
- **Media codecs:** Recording packet-copies H.264 or H.265/HEVC without transcoding; original AAC and G.711 A-law/μ-law audio remain in Matroska. Live View sends H.264/HEVC as fragmented MP4 with the appropriate codec metadata, but HEVC display requires the installed Windows WebView2/Linux WebKit runtime and OS to expose a compatible HEVC decoder; an accepted camera/profile is **not** proof that this machine can display it. Playback packet-copies AVC/HEVC into MP4, keeps AAC in MP4 and prepares G.711 as a session-scoped PCM WAV sidecar, played in sync with the video. There is no software H.265-to-H.264 fallback, video transcoding or RTSP audio talkback; HEVC decoding can fail on machines without codec support.
- **Recording capacity:** at most 8 simultaneous owned Recording sessions. Persisted Desired state beyond capacity remains Desired On but runtime admission fails deterministically.
- **Live capacity:** at most 16 simultaneous user-opened Live View sessions per visible page (1/4/8/16 layouts; additional selected cameras are paginated). This is a software admission limit, not evidence that a particular Windows machine can decode 16 cameras within its RAM/CPU budget. Leaving Live View unmounts the screen, explicitly tears down MSE/video resources and closes the page's backend live sessions; a later visit opens fresh sessions from the persisted camera/layout preference. Lifecycle Suspend/Quit/Update also settle transient live ownership and Resume does not resurrect stale session ids.
- **Event capacity:** at most 16 simultaneous ONVIF Event-monitoring sessions. Event Desired state is independent of Recording and remains persisted when runtime capacity is unavailable.
- **PTZ:** optional continuous pan/tilt and capability-gated zoom only. No presets, patrol/tours or talkback. PTZ movement does not restore after restart or Resume.
- **ONVIF compatibility:** discovery/provisioning/PTZ/Events depend on what a camera advertises and on standards-compatible behavior. Manual RTSP configuration remains valid when ONVIF is unavailable.
- **Events:** v1 stores normalized MotionStarted/MotionEnded history and maintains an independent Event product/clip plane with about five seconds of real pre-roll, five-second post-roll, immutable event-only clips and a hard maximum of five minutes per clip part. While ONVIF Events or the independently enabled Local Motion mode is enabled, the per-camera worker retains a bounded compressed main-stream packet ring (10 seconds, 32 MiB hard cap) instead of continuously writing Event media to disk. Motion capture atomically seeds a reliable Event recorder from that ring and then follows the same shared main ingest through motion/post-roll; manual Recording Desired, manual Start/Stop and Timeline ownership remain independent. Recording/Focus/Event capture therefore reuse one main RTSP connection, while a simultaneous Grid may additionally use one substream connection. Local Motion is opt-in and mutually exclusive with ONVIF Events: it compares sampled 32×18 luma thumbnails decoded from the shared substream (main fallback) to detect generic scene changes, not people, camera tampering or baby crying; its software decoder accepts H.264 or supported 8-bit HEVC luma video no larger than 1920×1080; unsupported decoded pixel formats fail closed. Detection thresholds are static, so no sensitivity/zone configuration is available yet. The worker transition queue is bounded but in-memory: an abrupt worker-process crash before a transition is committed to EventIndex can lose that uncommitted signal; the durable-commit-before-ACK protocol protects against lost ACK replies but does not make the worker queue crash-durable. ONVIF true/false state transitions can delimit episodes when the camera actually publishes both; a single Tapo push timestamp does not prove that the camera supplied an end time. If only a start arrives, the clip has a five-minute part cap and ongoing capture cannot be assumed to represent the true motion end. There is no Nian-side AI/person/object analysis, event thumbnail/export workflow or cloud Event archive. Camera-provided Tapo `PeopleDetector/IsPeople` transitions are separately classified as Person started/ended in Event Review (when that ONVIF topic is actually emitted), linked to an overlapping aggregate motion clip without opening a second recorder. `IsMotion` never inherits a Person label. Other Smart/LineCross signals remain generic motion compatibility inputs, not Nian AI; no local person/tamper/baby-cry model exists.
- **Notifications:** local desktop MotionStarted notifications only. No email, webhook, cloud push, schedules or quiet hours. The current desktop notification API does not provide the Event-id click callback required for reliable deep-link activation, so v1 does not pretend that it does.
- **Remote access:** no cloud streaming, WebRTC, remote server mode, multi-user/RBAC service or mobile access.
- **Signing:** Tauri updater signatures are mandatory release artifacts. Windows Authenticode depends on externally provisioned signing credentials and repository policy; source control never contains a private signing key.

## Tapo C200 interoperability status

TP-Link Tapo C200 is the reference camera target, but automated protocol/media tests and physical-device compatibility are different evidence. A final v1 release report must record real-device results separately for RTSP recording, Live View, ONVIF discovery/provisioning, PTZ and Events. Any item not manually exercised must be reported as unverified rather than inferred from automated fixtures.
